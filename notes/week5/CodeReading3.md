
# CodeReading3 集合源码阅读问答
## 问题1：Collection<EntityID> unexploredBuildings 为什么用Collection而不是List？
1. **接口抽象层级更高**
   Collection是List、Set的父接口，只约束「存储一组元素」的通用行为（add/remove/contains/isEmpty等），不强制有序、可索引的特性。
2. **业务不需要List特有能力**
   未探索建筑集合只需判断是否存在、新增/删除元素，不需要通过下标get(i)、按顺序排序、插入指定位置等List专属操作；
3. **实现类灵活切换**
   声明为Collection，底层可以自由切换HashSet、TreeSet等无重复集合，不会被List的有序特性限制；项目中此处实际使用HashSet，不允许重复建筑ID，List允许重复，不符合业务需求；
4. **解耦实现细节**
   上层代码只依赖最基础的集合规范，不绑定有序列表实现，降低代码耦合。

## 问题2：EnumSet.of(...) 是什么作用？对比普通Set有什么好处？
### 1. EnumSet.of() 作用
专门用于创建**枚举类型专用集合EnumSet**，批量传入枚举常量，快速初始化只存储枚举值的集合，仅能存放同一个枚举类的实例。

### 2. 对比普通HashSet的优势
1. **性能极强**
   底层用位掩码（bit数组）存储，增删查操作时间复杂度O(1)，内存占用远小于HashSet；
2. **无哈希冲突**
   枚举常量序号固定，不需要计算hashCode、处理冲突，逻辑简单高效；
3. **类型安全**
   编译期强制只能存入对应枚举，无法放入其他类型对象，避免类型转换异常；
4. **有序**
   内部自动按枚举常量定义顺序存储，遍历顺序稳定；
5. **API简洁**
   提供of()、allOf()、noneOf()等快速构造方法，初始化枚举集合代码更简洁。

### 适用场景
仅当集合元素全部是枚举类型时使用，项目中Agent类存储实体URN枚举，因此选用EnumSet。
